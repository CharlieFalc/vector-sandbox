STACKIT Telemetry Architecture

Interview Deep Dive — How OTEL, Vector, and STACKIT services fit together · Updated March 2026

The Big Picture: OTEL vs Vector — What They Each Do

The one-line answer: OpenTelemetry is the language (protocol + SDK + data model). Vector is the pipeline engine that speaks that language and does the heavy lifting of routing, transforming, and fan-out delivery. They're not competing — they compose.

OpenTelemetry (OTEL)

A CNCF standard that defines:

• SDKs — instrument your app code to emit spans, metrics, log records
• Data model — the schema for Trace, Metric, Log objects
• OTLP protocol — the wire format (protobuf over gRPC or HTTP) for shipping that data
• OTel Collector — a lightweight forwarder/preprocessor (optional, receiver → processor → exporter)

OTEL does not do heavy transformation, fan-out routing, disk buffering, or backpressure management at scale. That's where Vector takes over.

Vector (by Datadog, used by STACKIT)

A high-performance Rust pipeline engine that:

• Sources — ingests data: OTLP/gRPC, OTLP/HTTP, syslog, k8s logs, Kafka, etc.
• Transforms — VRL programs: redact PII, filter, enrich, reshape events
• Sinks — fans out to multiple destinations simultaneously
• Buffers — disk or memory buffers with backpressure propagation
• Acknowledgements — end-to-end delivery guarantees

Vector speaks OTLP natively — it's an OTLP-in, OTLP-out capable system, but can also bridge to non-OTLP sinks (S3, OpenSearch, Kafka, etc.).

Signal Type Breakdown: What Goes Where

Key insight: ALL three signal types (logs, metrics, traces) can travel over OTLP. Vector handles all three. The question is which signals STACKIT's Telemetry Router is actively routing today vs. what's on the roadmap.

Logs GA — Primary focus of Telemetry Router

This is where Telemetry Router started. Specifically:

  • Audit logs — platform-generated events (IAM changes, API calls, resource lifecycle). These are compliance-critical in a sovereign cloud. The Telemetry Router is replacing the old STACKIT Audit Log API as of March 2026.
  • Service logs — logs from STACKIT services (SKE, Object Storage, etc.) that customers need to see for debugging and compliance.
  • Application logs — customer app logs shipped via OTLP SDK or via OTel Collector sidecar.

All of these can land in STACKIT LogMe (OpenSearch), STACKIT Observability (Loki), S3 for archival, or a customer's external OTLP sink.

Metrics Handled separately today — roadmap for Telemetry Router

Today, metrics follow a different path: Prometheus scrape model via STACKIT Observability (Argus). Customer workloads expose /metrics endpoints; Prometheus scrapes them; Thanos handles long-term storage; Grafana visualizes. The Telemetry Router's "name implies broader ambition" — metrics routing is likely a future phase. This is a good interview question to probe.

Traces OTLP-native — flows through Telemetry Router or direct to Tempo

Distributed traces from OTel SDKs are exported via OTLP (gRPC :4317 or HTTP :4318). These can go directly to STACKIT Observability's Tempo backend, OR through the Telemetry Router if customers want fan-out (e.g., traces to both Tempo and an external tracing backend). Vector handles traces as OTLP events natively.

STACKIT's Visualization Layer — Not In-House

Short answer: STACKIT is not building their own visualization tool. They run a fully managed LGTM stack (Loki + Grafana + Tempo + Mimir/Thanos) as their hosted observability product ("Observability", formerly Argus). Customers who want full control can use the Telemetry Router to ship directly to their own external tool (Datadog, Splunk, Grafana Cloud, SigNoz, etc.).

STACKIT Observability (Argus) — Managed LGTM Stack

• Grafana — dashboards, alerting, explore
• Loki — log aggregation (multi-tenant)
• Tempo — distributed tracing storage
• Prometheus + Thanos — metrics + long-term storage
• Alertmanager — alert routing (supports Google Chat webhooks as of 2025)

Fully managed — STACKIT handles upgrades. Customer gets Grafana instance provisioned immediately. SSO via STACKIT IAM.

STACKIT LogMe — Managed OpenSearch

• OpenSearch — full-text search, log indexing
• Fluentd — log collection/forwarding agent
• OpenSearch Dashboards — ELK-style log exploration

Think of this as STACKIT's managed ELK/OpenSearch alternative to Loki. Customers who prefer SQL-like log queries or come from an ELK background will use this. Data stays in EU (German DCs) — GDPR compliant.

How It All Works: Step-by-Step Data Flow

Scenario A: Customer app traces → STACKIT Observability (Tempo)

1. Instrument the app with OTel SDK (Go example):

// main.go — OTel SDK bootstrapping
exp, _ := otlptracehttp.New(ctx,
    otlptracehttp.WithEndpoint("telemetry-router.stackit.cloud:4318"),
    otlptracehttp.WithHeaders(map[string]string{
        "Authorization": "Bearer <stackit-token>",
    }),
)
tp := trace.NewTracerProvider(trace.WithBatcher(exp))
otel.SetTracerProvider(tp)

2. App emits OTLP traces → hits Telemetry Router's OTLP HTTP source on :4318.

3. Vector routes to STACKIT Observability Tempo sink (conceptual Vector config):

# Conceptual Vector TOML — rendered by the K8s Operator from TelemetryRouter CRD
[sources.otlp_in]
type = "opentelemetry"
grpc.address = "0.0.0.0:4317"
http.address = "0.0.0.0:4318"

[transforms.enrich]
type = "remap"
inputs = ["otlp_in"]
source = '''
  # Tag with project ID for multi-tenancy routing
  .resource.attributes.stackit_project_id = "proj-xyz789"
  # Redact any Authorization headers from spans
  del(.attributes.http.request.header.authorization)
'''

[sinks.observability_tempo]
type = "opentelemetry"
inputs = ["enrich"]
endpoint = "https://ingest.observability.stackit.cloud:4317"
encoding.codec = "native_json"

[sinks.s3_archive]
type = "aws_s3"
inputs = ["enrich"]
bucket = "customer-telemetry-archive"
endpoint = "https://object.storage.eu-central-1.stackit.cloud"
region = "eu-central-1"
key_prefix = "traces/{{ "{{" }}%Y/%m/%d{{ "}}" }}/"

Scenario B: Platform audit logs → Customer's external SIEM

STACKIT platform emits audit events (e.g., "user created IAM role in project X") internally. The Telemetry Router's audit source ingests these and the customer configures a destination pointing to their SIEM:

# TelemetryRouter CRD (what a customer configures via STACKIT API/UI)
apiVersion: telemetry.stackit.cloud/v1alpha1
kind: TelemetryRouter
metadata:
  name: prod-router
  namespace: stackit-telemetry
spec:
  projectId: "proj-xyz789"
  region: "eu-central-1"
  replicas: 2

  sources:
    - type: AUDIT_LOGS       # STACKIT platform audit events
    - type: SERVICE_LOGS     # STACKIT service logs (SKE, object storage, etc.)
    - type: OTLP             # Customer app telemetry (logs + traces + metrics)

  transforms:
    - name: redact-pii
      vrl: |
        # Strip email addresses from log bodies
        .message = replace(string!(.message), r'\b[\w.]+@[\w.]+\b', "[REDACTED]")
        # Ensure data stays EU — drop events tagged non-EU
        if exists(.resource.attributes.region) {
          assert!(.resource.attributes.region == "eu-central-1",
                  "Non-EU data dropped for sovereignty compliance")
        }

  destinations:
    - name: "production-siem"
      type: OTLP
      endpoint: "https://ingest.siem.company.com:4317"
      secretRef: "siem-api-key"     # k8s Secret — never inline

    - name: "compliance-archive"
      type: S3
      bucket: "audit-archive-prod"
      endpoint: "https://object.storage.eu-central-1.stackit.cloud"
      region: "eu-central-1"

status:
  phase: Ready
  readyReplicas: 2
  conditions:
    - type: RegionCompliant
      status: "True"

Key Interview Answers — "How Does OTEL and Vector Play Together?"

Q: Are ALL metrics/logs/traces managed with OTEL then shipped via Vector?

Not exactly — the model is layered. Logs and traces are the primary signals flowing through the Telemetry Router today. Metrics currently flow via a separate Prometheus scrape path into STACKIT Observability. OTLP is the common protocol: OTel SDKs emit OTLP, and Vector's opentelemetry source/sink speaks OTLP natively. So: OTel defines the protocol and instruments the app; Vector is the pipeline that receives, transforms, and routes those OTLP events. They don't overlap — they compose.

Q: Is STACKIT building their own visualization UI?

No. STACKIT Observability is a fully managed Grafana stack (Loki, Tempo, Prometheus, Thanos). They're curating and operating best-in-class open source — not reinventing the dashboard. The Telemetry Router's job is to get the data to the right backend; visualization is handled by Grafana or by the customer's own tool.

Q: What does the K8s Operator actually do?

The operator watches TelemetryRouter CRDs. When a customer creates or updates one (via the STACKIT API), the operator reconciles: it renders a Vector TOML config from the CRD spec, manages the Vector Deployment/StatefulSet, handles rolling updates without dropping events (drain → upgrade → reconnect), and writes status back to the CRD. The operator is the bridge between "customer intent" (declared in the CRD) and "Vector reality" (running process with a specific TOML).

Q: What makes STACKIT different from Datadog OPs architecturally?

DD OPs is an enterprise cost-optimization product — the story is "route logs away from expensive backends." STACKIT's Telemetry Router is a sovereign cloud compliance primitive — every design decision flows from EU data residency and auditability. Multi-tenancy is a first-class constraint at STACKIT (one Vector config per customer, K8s operator-managed), whereas at DD, the pipeline workers are a shared fleet. Also: STACKIT is building the whole stack from scratch in Go + operator pattern; DD OPs built on top of an existing mature Vector deployment.

The Hardest Engineering Problem: Backpressure in Multi-Tenant Routing

This is what to study deepest. When one customer's SIEM sink goes down, backpressure propagates: sink buffer fills → transform queue fills → source stops ACKing → the OTLP client (their app) starts getting 429s or connection drops. In a shared cluster, one bad sink can starve other customers' pipelines unless isolation is enforced.

Vector's mitigation toolset:

  • Per-sink disk buffers — isolate sink failure from the rest of the topology. Cost: disk I/O can become a bottleneck (documented cases of 500 MB/s → 120 MB/s throughput regression when disk buffer is on).
  • Memory buffers with overflow-to-disk — faster steady-state, durable on spike. Best practice for production.
  • End-to-end acknowledgements — source only ACKs when the sink has confirmed delivery. Prevents silent data loss.
  • Separate Vector processes per customer — full isolation, higher resource overhead. The K8s operator makes this manageable.
  • VRL-level drop policies — explicitly drop low-priority events when buffer pressure exceeds threshold, rather than backpressuring the source.
